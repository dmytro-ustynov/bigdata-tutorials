### П2. Дані за структурою
Дайте визначення **структурованих**, **напівструктурованих** і **неструктурованих** даних
та наведіть по одному прикладу кожного типу.

<details><summary>Ключові пункти відповіді</summary>

- **Структуровані** — чітка схема (таблиці/рядки/стовпці); напр. CSV, реляційна БД, Excel.

### П3. SQL vs NoSQL
Назвіть основні відмінності між SQL (реляційними) та NoSQL базами даних і перелічіть
чотири типи NoSQL з прикладом кожного.

<details><summary>Ключові пункти відповіді</summary>

- **SQL:** фіксована схема, таблиці, гарантії ACID, для структурованих даних із чіткими
  зв'язками; вертикальне масштабування. Приклади: PostgreSQL, MySQL, Oracle.
- **NoSQL:** гнучка/відсутня схема, горизонтальне масштабування, для великих різнорідних даних.
- Типи: **документні** (MongoDB), **колонкові/сімейства колонок** (Cassandra, HBase),
  **графові** (Neo4j), **ключ-значення** (Redis).
</details>

### П4. Пакетна vs потокова обробка
Поясніть різницю між пакетною (batch) і потоковою (stream) обробкою. Наведіть по одному
інструменту та прикладу застосування для кожної.

<details><summary>Ключові пункти відповіді</summary>

- **Пакетна:** обробляє великі накопичені обсяги періодично; висока пропускна здатність, але затримка.
  Інструменти: Hadoop MapReduce, Spark. Приклад: щоденний звіт COVID-19 по всіх країнах.
- **Потокова:** обробляє дані в реальному часі у міру надходження; мінімальна затримка, малі порції.
  Інструменти: Kafka, Flink, Storm. Приклад: моніторинг температури пацієнтів через IoT-датчики.
</details>

### П5. Основи HDFS
Який стандартний розмір блоку та коефіцієнт реплікації в HDFS? Яка роль **NameNode**
порівняно з **DataNode**?

<details><summary>Ключові пункти відповіді</summary>

Стандартний розмір блоку **128 МБ**, коефіцієнт реплікації **3**.
**NameNode (master)** зберігає лише метадані — простір імен (дерево каталогів), відображення
файл→блоки та розташування блоків; самих даних не містить.
**DataNode (slave)** зберігає реальні блоки даних на локальному диску, надсилає heartbeat та
звіти про блоки до NameNode.
</details>

### П6. Конвеєр MapReduce
Перелічіть етапи конвеєра MapReduce по порядку та однією фразою поясніть кожен.

<details><summary>Ключові пункти відповіді</summary>

**Input → Split → Map → Shuffle & Sort → Reduce → Output.**
Input = вихідні дані; Split = фрагменти фіксованого розміру для мапера; Map = видача проміжних
пар (ключ, значення); Shuffle & Sort = групування значень за ключем і сортування; Reduce =
агрегація значень за ключем; Output = запис результатів у розподілену файлову систему.
</details>

### П7. Основні компоненти Hadoop
Назвіть три основні компоненти Apache Hadoop і зазначте відповідальність кожного.

<details><summary>Ключові пункти відповіді</summary>

- **HDFS** — розподілене зберігання даних у кластері (блоки + реплікація).
- **YARN** — керування ресурсами кластера та планування завдань.
- **MapReduce** — модель пакетних паралельних обчислень (Map → Reduce).
(Spark — швидший рушій обробки в пам'яті, що може замінити MapReduce.)
</details>

### П8. Що таке RDD?
Як розшифровується **RDD** і які три його ключові властивості?

<details><summary>Ключові пункти відповіді</summary>

**Resilient Distributed Dataset** — незмінна розподілена колекція, що обробляється паралельно.
- **Resilient (стійка)** — відновлювана з lineage, якщо втрачено партицію.
- **Distributed (розподілена)** — розбита на партиції по вузлах кластера.
- **Dataset (набір)** — колекція записів (об'єкти будь-якого типу).
</details>

### П9. Трансформації vs дії
У Spark: чим відрізняється **трансформація** від **дії**? Наведіть по два приклади кожної та
поясніть «ліниве обчислення».

<details><summary>Ключові пункти відповіді</summary>

- **Трансформації** визначають новий RDD із наявного і є **лінивими** (не виконуються до дії).
  Приклади: `map`, `filter`, `flatMap`, `reduceByKey`.
- **Дії** запускають обчислення й повертають результат драйверу або пишуть у сховище.
  Приклади: `collect`, `count`, `take`, `reduce`, `saveAsTextFile`.
- **Ліниве обчислення:** Spark лише записує трансформації як DAG (lineage) і обчислює весь
  ланцюг, коли викликано дію.
</details>

### П10. SparkContext vs SparkSession
Що таке `SparkContext` і що таке `SparkSession`? Що рекомендовано для нових застосунків і чому?

<details><summary>Ключові пункти відповіді</summary>

`SparkContext` (Spark 1.x) — початкова низькорівнева точка входу: підключення до кластер-
менеджера, створення RDD, broadcast-змінних, акумуляторів (один на JVM).
`SparkSession` (Spark 2.0+) — **уніфікована** точка входу, що обгортає SparkContext, SQLContext
і HiveContext та дає доступ до DataFrame, Dataset і SQL.
**Рекомендовано SparkSession** для всього нового коду; до RDD API дістаються через
`spark.sparkContext`.
</details>

# РІВЕНЬ 2 — СЕРЕДНІ (пояснити, порівняти, простежити)

### П11. Простежіть Word Count у MapReduce
Для наведеного входу (2 спліти) пройдіть етапи Map, Shuffle & Sort і Reduce та дайте
фінальні підрахунки.
`Спліт 1: "data is big data"`  `Спліт 2: "big data fast"`

<details><summary>Ключові пункти відповіді</summary>

- **Map:** С1 → (data,1)(is,1)(big,1)(data,1); С2 → (big,1)(data,1)(fast,1).
- **Shuffle & Sort:** big→[1,1], data→[1,1,1], fast→[1], is→[1].
- **Reduce:** **big:2, data:3, fast:1, is:1**.
</details>

### П12. Блоки та репліки HDFS
Файл 512 МБ зберігається в HDFS (розмір блоку 128 МБ, реплікація 3). Скільки буде блоків і
скільки всього реплік блоків? Поясніть, що дає **rack awareness**.

<details><summary>Ключові пункти відповіді</summary>

512 ÷ 128 = **4 блоки**; 4 × 3 = **12 реплік**.
**Rack awareness:** HDFS розміщує репліки на різних стійках, щоб файл пережив відмову цілої
стійки. Типова політика при RF=3: 1-ша репліка на вузлі локальної стійки, 2-га — на вузлі
іншої стійки, 3-тя — на ще одному вузлі тієї ж другої стійки (баланс відмовостійкості й
пропускної здатності запису).
</details>

### П13. Чому Spark швидший за MapReduce
Поясніть, чому Spark швидший за MapReduce, особливо для **ітеративних** алгоритмів
(напр. машинне навчання).

<details><summary>Ключові пункти відповіді</summary>

MapReduce записує проміжні результати на диск після кожного етапу, тож кожна ітерація знову
читає й пише HDFS. Spark тримає дані **в пам'яті** між операціями та може один раз **кешувати**
RDD/DataFrame і повторно використовувати між ітераціями, уникаючи дискового I/O — до ~100×
швидше. Також використовує довільний **DAG** етапів замість фіксованих map→reduce і
відмовостійкість на основі lineage замість реплікації.
</details>

### П14. Архітектура YARN
Опишіть ролі **ResourceManager**, **NodeManager**, **ApplicationMaster** та **Container** у YARN.

<details><summary>Ключові пункти відповіді</summary>

- **ResourceManager (master):** глобальний розподіл ресурсів через **Scheduler** плюс
  **ApplicationsManager**, що приймає завдання і перезапускає збійні AM. Не моніторить задачі.
- **NodeManager (на вузлі):** керує контейнерами, моніторить їх CPU/пам'ять, шле heartbeat,
  вбиває контейнери, що перевищили ліміти.
- **ApplicationMaster (один на застосунок):** узгоджує контейнери з RM, запускає й моніторить
  задачі, перезапускає збійні.
- **Container:** ізольований виділ CPU+пам'яті на вузлі, де виконується задача/executor.
</details>

### П15. Локальність даних
Що означає «переносити обчислення до даних» і чому локальність даних важлива у розподіленій
обробці?

<details><summary>Ключові пункти відповіді</summary>

Замість пересилання великих даних мережею до програми фреймворк запускає програму (map-задачу)
на вузлі, який уже містить потрібний блок даних. Це мінімізує мережевий трафік — найдорожчу
частину розподіленої обробки — і підвищує пропускну здатність. І MapReduce, і читання HDFS
використовують локальність (клієнт читає з найближчого DataNode).
</details>

### П16. Ліниве обчислення, DAG та ієрархія завдань
Чому Spark використовує ліниве обчислення і що таке DAG? Поясніть ієрархію
Application → Job → Stage → Task та що позначає межу стадії.

<details><summary>Ключові пункти відповіді</summary>

Ліниве обчислення дає Spark побачити **весь** розрахунок до запуску, щоб оптимізувати
(конвеєризувати трансформації, пропускати зайве). Записаний план — це **DAG** трансформацій.
**Job** запускається дією; ділиться на **Stages**, обмежені **shuffle**; кожна Stage має по
одній **Task на партицію**, що виконується на executor. У межах стадії задачі йдуть паралельно
без обміну даними.
</details>

### П17. Відмовостійкість: lineage vs реплікація
Порівняйте, як HDFS і Spark досягають відмовостійкості. Чому lineage ефективний для
обчислювально важких навантажень?

<details><summary>Ключові пункти відповіді</summary>

**HDFS** реплікує кожен блок (типово ×3); при відмові вузла дані обслуговує інша репліка, а
NameNode відновлює втрачені блоки. **Spark** використовує **lineage**: кожен RDD пам'ятає
трансформації, що його створили, тож втрачена партиція **переобчислюється** з батьківської —
без зайвого сховища/мережі на реплікацію. Lineage ефективний для важких обчислень у пам'яті,
бо переобчислюється лише втрачена партиція, а не дублюються всі дані.
</details>

### П18. Інструменти екосистеми Hadoop
Опишіть призначення щонайменше чотирьох із цих інструментів та їх категорію: Hive, Pig, HBase,
Sqoop, Flume, Kafka, ZooKeeper, Oozie.

<details><summary>Ключові пункти відповіді</summary>

- **Hive** — SQL-подібні запити до даних у HDFS (доступ до даних).
- **Pig** — високорівнева мова скриптів для перетворень (доступ до даних).
- **HBase** — NoSQL БД сімейств колонок поверх HDFS (сховище).
- **Sqoop** — перенесення даних між РСКБД і HDFS (завантаження).
- **Flume** — збір/агрегація логів у HDFS (завантаження).
- **Kafka** — розподілена платформа потоків для завантаження в реальному часі.
- **ZooKeeper** — служба координації/конфігурації/синхронізації.
- **Oozie** — планувальник робочих процесів, що з'єднує завдання Hadoop.
</details>

### П19. DataFrame vs RDD
Чому для структурованих даних краще використовувати DataFrame API / Spark SQL, ніж «сирі»
RDD? Назвіть оптимізатор і одну оптимізацію, яку він виконує.

<details><summary>Ключові пункти відповіді</summary>

DataFrame мають схему й оптимізуються **Catalyst** (RDD — ні, оптимізує користувач вручну).
Catalyst будує логічний → оптимізований → фізичний план і застосовує оптимізації, як-от
**predicate pushdown** (фільтри до groupBy/сканування) та відсікання стовпців, тож обробляються
лише потрібні стовпці/рядки. Це дає кращу продуктивність і лаконічніший код, ніж ручні RDD.
</details>

### П20. Lambda-архітектура
Опишіть Lambda-архітектуру. Що робить кожен із трьох її шарів?

<details><summary>Ключові пункти відповіді</summary>

- **Batch layer** — повна точна обробка всіх історичних даних.
- **Speed layer** — обробка нових даних у реальному часі з низькою затримкою.
- **Serving layer** — об'єднує результати batch і speed для відповіді на запити користувача.
Поєднує пакетну й потокову обробку: користувач отримує і точні історичні дані, і актуальні дані
в реальному часі.
</details>

# РІВЕНЬ 3 — СКЛАДНІ (проєктування, обчислення, кілька концепцій)

### П21. Проблема обчислювальної функції
Поясніть проблему обчислювальної функції. Чому `sum()` розкладається по партиціях, а
`median()` — ні? Перелічіть механізми, якими Spark зменшує вартість shuffle.

<details><summary>Ключові пункти відповіді</summary>

Обчислити `f(D)` над даними, розподіленими по вузлах, складно, бо переміщення даних дороге і не
кожна функція збирається з часткових результатів.
- **`sum`** **розкладна**: часткові суми по партиціях, потім сума часткових.
  **`mean`** частково розкладна (потрібні sum + count). **`median`** **не розкладна** — потрібен
  повний відсортований набір, що змушує shuffle всіх даних.
- Spark зменшує shuffle через: **ліниве обчислення + оптимізацію DAG**; розрізнення **вузьких**
  (map, filter — без shuffle) і **широких** (groupByKey, join — shuffle) залежностей та
  конвеєризацію вузьких; **партиціонування** для co-location ключів; **broadcast-змінні** для
  малих довідкових даних; **акумулятори** для розподілених лічильників.
</details>

### П22. Спроєктуйте детектор brute-force (Structured Streaming)
За допомогою Spark Structured Streaming на Kafka-топіку `security-events` спроєктуйте детектор
brute-force входів. Вкажіть вікно, поріг, watermark, чому не можна точний distinct і як писати
алерти в PostgreSQL.

<details><summary>Ключові пункти відповіді</summary>

Фільтруємо `event_type = "auth_attempt"` і `result = "failed"`, групуємо за **ковзним вікном**
(напр. `window(timestamp, "2 minutes", "30 seconds")`), `source_ip` і `destination_ip`;
`count()` і лишаємо групи з `count >= 5`. Додаємо `.withWatermark("timestamp", "…")` для
обробки запізнілих подій і скидання старого стану вікон. Точний `distinct` на потокових
DataFrame не підтримується, тож для унікальних користувачів/джерел беремо
**`approx_count_distinct`**. JDBC не може бути прямим потоковим приймачем, тож пишемо через
**`foreachBatch`** (режим append) з **checkpointLocation** у таблицю `brute_force_alerts`.
Очікування: алерти за 2–3 хв від початку атаки.
</details>

### П23. Watermarking і запізнілі дані
Що таке watermark у Structured Streaming і яку проблему він вирішує? Як режими виводу
(append / update / complete) взаємодіють із ним і в чому компроміс вибору тривалості watermark?

<details><summary>Ключові пункти відповіді</summary>

**Watermark** = поріг за часом події `max(час події) − затримка`; Spark вважає, що даних,
старіших за watermark, не надійде, тож може **фіналізувати віконні агрегації** і скинути їх
стан (обмежує пам'ять). Події, старіші за watermark, відкидаються як «занадто пізні».
Режим **append** видає результат вікна лише після фіналізації (коли watermark пройде) — типово
для віконних агрегацій; **update** інкрементально видає змінені рядки; **complete** щоразу
видає всю таблицю результатів (стан не скидається). **Компроміс:** довший watermark ловить
більше запізнілих даних, але відкладає фіналізацію і тримає більше стану; коротший — швидший і
економніший, але відкидає більше пізніх подій.
</details>

### П24. Повний шлях запису в HDFS і відновлення після збою
Опишіть, що відбувається, коли клієнт записує файл у HDFS (конвеєр блоків, роль NameNode,
розміщення реплік). Тоді поясніть, що станеться, якщо ціла стійка втратить живлення.

<details><summary>Ключові пункти відповіді</summary>

1. Клієнт просить **NameNode** створити файл; NameNode повертає список DataNode для першого
   блоку. 2. Клієнт передає блок на DataNode 1, який **конвеєром** пересилає його на DataNode 2,
   потім на DataNode 3; ACK ідуть назад по конвеєру. 3. Самі дані ніколи не проходять через
   NameNode (лише метадані). 4. Репліки розміщуються за **rack awareness** (локальна + друга
   стійка).
Якщо **стійка** втрачає живлення, блоки лишаються доступними з реплік на інших стійках (тому
2-га/3-тя репліки — на іншій стійці). NameNode виявляє відсутні **heartbeat** і наказує вцілілим
DataNode створити нові репліки, щоб відновити фактор 3. Дані не втрачаються, доки виживає ≥1
репліка кожного блоку.
</details>

### П25. Життєвий цикл застосунку YARN і планувальники
Опишіть життєвий цикл застосунку YARN від подання до завершення. Тоді порівняйте планувальники
FIFO, Capacity і Fair та коли який доречний.

<details><summary>Ключові пункти відповіді</summary>

**Життєвий цикл:** клієнт подає застосунок до RM → RM просить NodeManager виділити контейнер і
запускає **ApplicationMaster** → AM реєструється в RM і запитує ресурси → RM виділяє контейнери
за політикою → AM каже NodeManager запустити контейнери задач → задачі звітують AM про прогрес →
по завершенні AM повідомляє RM і звільняє ресурси.
**Планувальники:** **FIFO** — одна черга, перший прийшов-перший обслужений (велике завдання
блокує все; лише для тестів). **Capacity** — кілька черг із гарантованою мінімальною ємністю,
можуть позичати вільні ресурси (багатокористувацький продакшн; типовий в Apache). **Fair** —
порівну розподіляє ресурси між застосунками (інтерактивні навантаження, де кожне завдання має
отримати справедливу частку).
</details>

### П26. Spark у кластері: стадії та залежності
Поясніть, як Spark-застосунок виконується в кластері (driver, executors, cluster manager) і як
завдання ділиться на стадії й задачі. Що створює межу стадії? Наведіть приклад вузької та
широкої залежності.

<details><summary>Ключові пункти відповіді</summary>

**Driver** виконує `main()`, будує DAG, узгоджує ресурси з **cluster manager** (YARN/K8s/
Standalone) і планує **задачі** на **executors** (JVM на вузлах, що виконують задачі й кешують
дані). **Дія** запускає **Job**; DAG-планувальник ділить його на **Stages** на межах **shuffle**;
кожна стадія — по одній **Task на партицію**. Межу створює **shuffle** (широка залежність).
**Вузькі** залежності — `map`, `filter` (кожна батьківська партиція живить одну дочірню,
конвеєризуються в одну стадію). **Широкі** — `groupByKey`, `reduceByKey`, `join` (дані
обмінюються між партиціями → нова стадія).
</details>

### П27. Масштабування з 205 МБ до 205 ГБ і master-URL
Ваше Spark-завдання над логами NASA працює на ~205 МБ локально. Що зміниться, якщо набір стане
205 ГБ — код, кластер чи обидва? Поясніть master-URL `local[*]`, `local[N]`, `yarn`, `k8s://…`
та коли який доречний.

<details><summary>Ключові пункти відповіді</summary>

**Код застосунку майже не змінюється** (абстракції Spark не залежать від масштабу); змінюється
**кластер/розгортання**: з однієї машини — на багатовузловий кластер, запуск на YARN/Kubernetes,
більше executor/пам'яті, достатньо партицій і shuffle-ємності, читання з HDFS/S3 замість
локального файлу. Кешуйте вибірково (205 ГБ не влізе в RAM). **Master-URL:** `local[*]` = локально
на всіх ядрах (розробка/тести); `local[N]` = локально з рівно N потоками; `yarn` = на кластері
Hadoop YARN (найтиповіший продакшн); `k8s://…` = на кластері Kubernetes (контейнеризоване
розгортання).
</details>

### П28. Розподілена класифікація з MLlib
Як Spark MLlib тренує класифікатор у розподілений data-parallel спосіб? Чому тут важливе
кешування Spark у пам'яті? Порівняйте Logistic Regression, Random Forest і Naive Bayes та
скажіть, коли який найкращий.

<details><summary>Ключові пункти відповіді</summary>

**Data-parallel тренування:** дані розбиті по вузлах; кожен executor обчислює **локальні
градієнти** на своїй партиції; градієнти **агрегуються (reduce)** по вузлах; параметри моделі
**оновлюються**; кроки повторюються до збіжності. Оскільки тренування **ітеративне**, кешування
даних у пам'яті між ітераціями уникає повторного читання з диска — саме тут Spark випереджає
MapReduce.
- **Logistic Regression** — лінійна, інтерпретована; хороший базовий вибір для бінарної/
  багатокласової; масштабується розподіленим градієнтним спуском.
- **Random Forest** — ансамбль дерев, тренованих паралельно на вибірках; висока точність, менше
  перенавчання, нелінійні зв'язки + важливість ознак.
- **Naive Bayes** — ймовірнісний, однопрохідна агрегація лічильників; дуже швидкий; чудовий для
  класифікації тексту / високовимірних розріджених даних.
</details>

### П29. Hadoop Streaming — напишіть і поясніть
Поясніть, як працює Hadoop Streaming (контракт вводу/виводу, формат ключа, хто сортує). Тоді
напишіть Python-мапер і -редьюсер, що рахують **сумарне населення по країнах** із CSV-рядків
`city,country,continent,population,lat,lng`. Чому спершу тестувати локально?

<details><summary>Ключові пункти відповіді</summary>

**Streaming** дозволяє писати MapReduce будь-якою мовою: мапер і редьюсер — програми, що читають
`stdin` і пишуть `stdout`; мапер видає `key\tvalue` (через табуляцію); **фреймворк сортує** весь
вивід мапера за ключем перед редьюсером, який отримує ключі згрупованими.
```python
# mapper.py
import sys
for line in sys.stdin:
    line = line.strip()
    if line.startswith("city,"):      # пропустити заголовок
        continue
    p = line.split(",")
    print(f"{p[1]}\t{p[3]}")           # країна, населення
```
```python
# reducer.py
import sys
cur, total = None, 0
for line in sys.stdin:
    key, val = line.strip().split("\t", 1)
    val = int(val)
    if key == cur:
        total += val
    else:
        if cur is not None: print(f"{cur}\t{total}")
        cur, total = key, val
if cur is not None: print(f"{cur}\t{total}")
```
Локальний тест (`cat cities.csv | python mapper.py | sort | python reducer.py`) дешево ловить
помилки логіки/парсингу до повільного запуску в кластері. **Плюс:** будь-яка мова / швидко писати;
**мінус:** повільніше й менш типобезпечно, ніж нативний Java MapReduce.
</details>

### П30. DDoS vs brute-force і наскрізний конвеєр
Порівняйте потокову логіку виявлення **DDoS** та **brute-force** атак (тип події, вікно, поріг,
метрики). Чому потокова обробка забороняє точний distinct і що використовують натомість?
Накресліть повний конвеєр даних лабораторії.

<details><summary>Ключові пункти відповіді</summary>

- **Brute force:** `event_type=auth_attempt`, `result=failed`, групування за `source_ip` +
  `destination_ip` у ~2-хв ковзному вікні; алерт, коли кількість невдач ≥ поріг (напр. 5).
- **DDoS:** `event_type=network_connection`, групування за **ціллю** `destination_ip` у ~1-хв
  вікні; алерт, коли `request_count ≥ ~100`, і відстеження `approx_count_distinct(source_ip)` як
  унікальних джерел — DDoS це великий **обсяг від багатьох джерел до однієї цілі**, brute force —
  багато **невдалих входів з одного джерела**.
- Потокова обробка не підтримує точний `count(distinct …)` (потрібен необмежений стан), тож
  використовують **`approx_count_distinct`** (HyperLogLog).
- **Конвеєр:** Log Generator (Node.js) → **Kafka** (`security-events`) → **Spark Structured
  Streaming** (парсинг `from_json`, агрегації з вікном + watermark) → **PostgreSQL** через
  `foreachBatch` (`brute_force_alerts`, `ddos_alerts`, …), з Spark UI / Kafka UI / pgAdmin для
  моніторингу.
</details>
